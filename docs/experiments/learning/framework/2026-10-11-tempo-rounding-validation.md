# 手番係数のメモリ上摂動と実エンジンの整数丸め検証

2026年10月11日。滑らかな損失・勾配の検証は `a1305fd` にコミットした。
本段階では、専用probeの私有メモリ内で手番係数を固定幅だけ変え、
評価の整数計算を別実装で照合した。探索・学習更新・評価ファイル保存は行っていない。
通常エンジンと元データを変更せず、暫定入力と固定25cp補正を維持した。

## 検査の実装

`learning_data_probe.cc` に `--evaluate-details` と `--perturb-tempo` を追加した。
前者はKP合計、その他の評価合計、手番係数のpacked整数値を出力する。
後者は指定paramsを読み込んだ後、手番の最初の3成分だけへraw整数差分を加える。
差分は各成分±5cp以内、全成分を検査してからメモリへ適用する。
第4成分は変更せず、ファイルへ書き出す経路はない。

`prepare_learning_data.Probe` の任意引数でこれらの検査モードを選べるようにした。
従来の再生・静的評価モードの既定動作は維持している。
`tools/check_tempo_rounding.py` はtrainの固定ルートだけを使い、
次の2つを独立に確認する。

1. packed値から整数評価を再構成し、ネイティブの `ComputeFinalScore` と厳密照合する。
   進行度の65536分の1への量子化、途中の10／2での除算、最後のcpへの除算を含む。
2. 手番以外のKP／評価成分、進行度、盤面、手番、Huffmanが不変であること、
   要求した3つのraw差分だけが手番係数に入ったことを確認する。

負数の除算はC++の0方向への切り捨てを再現する。
Pythonの `//` は負数で下方向へ丸めるため、そのまま置き換えてはいけない。
前段の滑らかな式との差分にも符号・進行度・1/2係数を用いる。
ベースと摂動後の両方で丸め誤差があり、0を跨ぐ場合は変化量の誤差が
1cpを超えることもあるため、一般的な上限は約2cpとして検査した。

## 実データの結果

```sh
make learning-probe -j2
python3 -m unittest discover -s test -p 'test_tempo*.py' -v
python3 -m unittest discover -s test -p 'test_*learning*.py' -v
python3 tools/check_tempo_rounding.py \
  results/learning-pilot/2026-10-11-preparation-v2/manifest.json \
  --output results/learning-pilot/2026-10-11-input-validation-v1/tempo-rounding-v1.json
```

固定ベースのtrain1,024局面を使い、10種類の摂動でON/OFF双方を検査した。
全20,480評価が別実装の整数計算と完全一致した。
ベース・摂動後とも教師のルートだけを評価し、静止探索や教師PVの末端は使っていない。

| 手番3係数の変更量（cp） | ON/OFF合計の評価変化件数／2048 | 滑らかな変化量との最大誤差cp |
| --- | ---: | ---: |
| `(0,0,0)` | 0 | 0 |
| `(+1,0,0)` | 155 | 0.970520 |
| `(-1,0,0)` | 172 | 0.974960 |
| `(0,+1,0)` | 750 | 0.801437 |
| `(0,-1,0)` | 787 | 0.844513 |
| `(0,0,+1)` | 112 | 0.961044 |
| `(0,0,-1)` | 112 | 0.982391 |
| `(+0.25,-0.5,+0.75)` | 298 | 0.955708 |
| `(-0.25,+0.5,-0.75)` | 266 | 0.970051 |
| `(1/65536,0,0)` | 0 | 0.0000047523 |

ここでの「変化件数」は局数や棋力指標ではない。
小さな差分は整数cpへ反映されない場合がある。従って、整数エンジン評価を
0.001cpの微小幅で差分して得た0を、解析勾配が間違っている証拠にはしない。
学習時のfloat状態と、エンジン用整数評価への反映を区別する必要がある。
今回の範囲では誤差は1cp未満だったが、一般の上限まで1cpと狭めてはいけない。

新しい6テストを含む関連32テストが成功した。
符号付き除算、両色の手番係数、手番を持つ他成分、0を跨ぐ丸め、
摂動値の範囲・型の拒否、ネイティブの手番以外の成分と元ファイルの保持を確認した。

## 成果物と残る検証

結果JSONのSHA-256：
`2e42f6a0794f0931e9387189130c39ec63238305e1afdf47d3b4ddcc31990e45`。
probe SHA：`28b5fddc41af71b0bcfb54e647f2e14a6f729cdede4570c2920a20ebd4e225cd`。
元manifest・分割・checkpoint・過去の検証結果は上書きしていない。
通常バイナリ、4つのbinデータ、共通定跡の6ファイルのSHAも前後で不変。
`updates: 0`、`parameter_files_written: false`、`training_ready: false` を保持した。

これで、固定された静的ルートについて、滑らかな手番係数の式と
実エンジンの整数評価の関係を確認できた。
次は静止探索の末端を固定して、ルート／末端の手番・符号・評価・進行度を
同じ方法で照合する。PVの切替やoptimizerの学習更新はまだ検証していない。
小規模な学習実行は、この接続検証と実験条件の確定後の別段階とする。
