# 探索教師候補と現行版：８開始局面・16局の試走

2026年10月17日。[指し手比較](2026-10-17-hybrid-behavior-result.md)で24局面中6局面の
最善手が変化した。ユーザーの了承を受け、候補を固定して小規模対局を準備する。
挙動比較までの実装・結果はコミット `46300be`（この時点では未push）。

## 目的

静的な予測誤差の改善が、実戦で役立つかを探る入口。
まず、大きな悪化や未決着の多発がないかと、金銀の支え・前進・受けに戻る判断を
実際の棋譜で見る。16局では棋力向上の確定や現行評価への採用を判断しない。
追加学習、混合率の調整、特定の手を正解とする追加教師は挟まない。

## 開始局面と先後交代

[固定した８手順](../../configs/hybrid-match-starts-v1.json)を使用。
いずれも12手進めた序盤から開始する。

- 先手が▲４八玉から組む４種類：後手は四間飛車・三間飛車・中飛車・居飛車。
- 後手が△６二玉から組む４種類：先手は四間飛車・三間飛車・中飛車・居飛車。
- 各開始局面から候補先手／現行版後手、現行版先手／候補後手の２局。計16局。
- 手順は人為的に固定し、候補の探索点や対局結果で選んでいない。
- 開始局面が学習・検証・診断の469元局面と同一でないことを確認する。ただし、
  定型的な序盤なので過去棋譜の途中と重なりうる。無作為抽出や未知局面の標本とは呼ばない。
- 先後を替えるのはエンジンの担当。盤面・開始手順は同じで、盤面を反転しない。

## 対局条件

| 項目 | 固定条件 |
| --- | --- |
| 現行版 | hybrid学習時に保存したbaseline runtime |
| 候補 | search教師のみ・63更新の最終候補、監査済みexport |
| 両版の設定 | 新米長玉ON・定跡OFF・Threads1・Hash64MB・ponder OFF |
| 思考量 | 毎手depth15。通常のcp応答は深さ到達を確認。詰みで早く終えた場合は別記 |
| 応答待ち上限 | 毎手30秒。timeoutは実行エラーで、負けにしない |
| 起動 | １局ごとに両版を新規起動。局内では探索状態を保持 |
| 手数上限 | 開始後256手。勝敗がつかなければ未決着 |
| 評価値による裁定 | なし。大きな評価差だけで勝敗を決めない |

固定深さは同じ持ち時間ではない。候補で探索量が増えた局面もあったので、今回は
同深さでの試走として扱う。勝ちやすさと計算効率を合わせて判断するには、その後の
同じ時間条件による確認が必要。棋譜には各手の探索情報とログを残す。

最大4096手を指す設定。毎手30秒を全部使えば探索待ちだけで約34時間になるが、
これは上限で所要時間の予測ではない。前回の局面比較は48探索の合計が約17秒だったが、
終盤や局内の探索状態も違うため、その速度から対局時間を保証しない。

## 判定と保存

対局専用のnative refereeを独立ビルドする。現行エンジン・学習probe・評価データは
変更しない。refereeは評価・探索を行わず、駒の動きとルールを検証する。

- 全履歴を合法手で再生。二歩・打ち歩詰め等もチェック。
- 盤面・持駒・手番が同じ局面の４回出現を判定。探索用の簡略な反復判定は使わない。
- その区間で一方が連続王手していれば王手側の負け、それ以外は千日手引分け。
- 合法手がなければ手番側の負け。詰みとそれ以外を理由で区別。
- 投了は負け。入玉宣言は現行エンジンと同じCSA条件を検証してから勝ち。
- 不正な手・不正な宣言・通信失敗はエラーとして停止し、勝敗集計に混ぜない。
- 手数打切りは未決着。引分けに含めない。

１手ごとに途中棋譜とログを保存し、１局完了ごとに集計する。
同じrunコマンドで完了局は飛ばす。失敗局・途中のattemptは自動でやり直さない。
中断した場合は記録を残し、次の扱いを確認する。markerの削除や条件変更はしない。
両局が揃った組数と未完の組数、候補の先後別成績を併記し、片側だけの結果を隠さない。

通常の `bestmove 8f8g` があり、受信前にstopを送っていない。

`src/search.cc` のIterativeDeepeningは大きい評価値のときinfo表示を間引き、
最終反復のinfoを必ず表示する仕様ではない（419～432行付近）。

正常なbestmoveを受け取った場合、表示されたdepthが1～15なら指し手を合法性検証へ渡す。
表示depthが要求未満なら `reported_depth_below_requested`、表示PVの先頭がbestmoveと
異なる場合は `reported_pv_differs_from_bestmove` を記録する。

## v3第２局のtimeoutとv4への移行

v3は第２局の112手まで進んだ後、現行版（先手）の次の探索が30秒を超えた。
ログにはdepth14/time1640msの後、ツールのstop送信に続きdepth15/time30004ms、
`bestmove resign` が残る。停止後の応答なので、この投了を候補の勝ちに数えない。
プロセス異常終了ではなく、要求深さの探索中に応答待ち上限へ達した事例。
局面比較用の短い待ち時間を対局にも使った設定が適切でなかった。

思考要求 `go depth 15`、エンジン、候補、referee、開始局面、対局順は維持し、
両版の応答待ち上限だけ30秒から300秒へ変更。これは持ち時間を５分にする変更ではなく、
深さ15の応答を待つ監視タイマーの延長。timeout時のstop・失敗記録は継続する。
ツールに埋め込まれていた30秒も除き、凍結したplanのdepth/timeoutを呼出しに渡す。
両担当で300秒が使用される回帰テストを追加し、対局実行関連10テスト通過。
