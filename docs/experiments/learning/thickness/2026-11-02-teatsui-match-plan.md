# 手厚い棋風：加点0対10の16局予備対局

ユーザーは加点10で対局した結果を見たいと希望し、強さが変わらない程度なら
個性としての採用も候補に挙げた。準備・検査は完了。当初は本対局未開始。現在は第1局が300秒timeoutで停止済み。
[診断と時間上限つきの新計画](2026-11-03-teatsui-timed-match.md)を参照。
長時間実行はユーザーの端末で行い、設計・結果解釈はAstraが担当する。

## 固定条件

- 同一のO2/assert有効バイナリを２つの隔離ディレクトリにコピー。
  仮想取り返し・合法手ゼロの両修正を含む。元バイナリとコピーのSHA一致。
- baseline加点0、candidate加点10。それ以外は同じ。どちらも新米長玉ON。
  支持関係の加点は各エンジンの中で先後対称。
- 既存 `hybrid-match-starts-v1.json` の８開始局面を全て使用。
  先手新米長玉の４型・後手新米長玉の４型、各12手の履歴を固定。
  各開始局面でcandidateを先後入れ替え、最大16局。既知の開発用開始局面であり未見評価ではない。
- 深さ15、thread1、hash64、定跡・ponderOFF、各局新規プロセス。
  １手300秒上限、開始後256手上限。時間切れはエラー、手数上限は未決着。
  同一時間の棋力比較ではなく、固定深さの予備試験。
- 専用native refereeが全着手を再生し、合法性、千日手、連続王手の千日手、
  詰み、入玉宣言を判定。投了も記録。評価値だけの勝敗打ち切りはしない。
- 途中結果を各手保存、各局の試行マーカーを先に作る。
  異常終了は全体を停止。未完了局・失敗局の自動再試行は禁止。
  完了済み局の境界からの再開は同じrunコマンドで可能。
  run.lockで二重実行を防ぐ。勝敗を見て局数・係数を変更しない。

## 判定方針

candidateの勝敗・引分・未決着・エラー、先後別成績、同じ開始局面での２局をまとめる。
手数上限を引分として勝率に混ぜない。固定開始局面と２局の関連を無視して
16個の独立標本から棋力差を精密に推定した扱いにしない。

この規模では僅かな弱化や棋力同等を証明できない。
五分に近くても自動採用せず、指し方の好み、繰り返す無理な進出や守備の穴、
計算コスト、未決着・エラーを別々に確認する。勝った好例だけを選ばず、
各開始局面の両局と負け方も見る。問題があれば原因診断を優先する。
好みが維持され大きな問題が見えなければ、より広い条件での確認または
不確実性を承知した任意の棋風設定としての試験採用をユーザーと相談する。
今回の実行に既定値変更、運用バイナリ反映、学習、係数探索は含まない。

## 準備・検査

既存の `tools.learning.playtest.match` の対局進行・保存・集計と
`RecordedEngine`、native refereeを再利用。試験固有の接続コードだけローカルに保存。
実行コード・ソース・開始局面・バイナリ・評価データのハッシュを固定し、
開始・終了時に照合する。運用bin/releaseは読み取りのみ。

- 新しい隔離refereeをビルド。対局とrefereeの既存25テストが成功。
- ８開始履歴が合法・非終局・重複なしであることをrefereeで確認。
- 加点0/10を最初のisready前に設定したことをコマンド列で確認。
- 各側１回、深さ3の接続検査を行い、返った手をrefereeで合法性確認。
  この２探索は対局結果に含めない。
- 最初の起動確認でbook.bin不在を検出。OwnBook=falseでも起動時に読むため、
  読み取り用リンクを追加。失敗時点でgoコマンド・対局は0。
  旧計画はpreflight-plan-v1.json、理由はpreflight-failure-v1.jsonに保持し、
  本対局開始前に新しいplan.jsonを固定した。

cd /Users/yuzo.iwasaki/Rakuyou
caffeinate -i python3 results/teatsui-match-2026-11-02/match.py run

`games/*.partial.json` で進行中の棋譜を確認できる。
