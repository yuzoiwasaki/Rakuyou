# 手厚さ・玉の安全性と支持形加点の関係

組4・組7の[対局レビュー](2026-11-07-normal-comparison-result.md)を受けて、
既存評価の構造と保存局面の静的評価を確認する。エンジン・係数・学習データは変更しない。

## ユーザーから得た判断軸

- 好みの形ができても、その後に備えを保ってじっくり指せるとは限らない。
- 自玉の固さ、相手から攻められているか、侵入駒への対応を含めて厚みを見る。
- 組4は32手目では0/10とも好み、48手目では0の落ち着いた手厚さを好む。
  10は玉3九・飛2九が近いまま攻め合いになり、ユーザーはやや悪そうと判断。
- 組7は32手目では10を好むが48手目では0。4一馬の裏からの攻めに対し、
  2筋に手をかける時機が気になる。5五歩〜同銀は6五桂で逆用されているとの見立て。

この判断を、近い玉飛車の一律減点や2筋の歩の禁止、特定の敗着認定に変換しない。

## 既存コードが見ているもの

| 項目 | 実装 | 入力として見ているもの・限界 |
| --- | --- | --- |
| 玉の安全性 | `src/evaluation.cc` の `EvaluateKingSafety` | 玉の周囲8マスの駒と攻守の利き、相手の持ち駒の種類、隅玉フラグ。守備の利きは玉自身を除き、攻守とも最大3。持ち駒枚数そのものはこの索引に入らない。 |
| 玉と駒の位置関係 | `EvaluatePositionalAdvantage`、`EvalParameters::king_piece` | 玉と各駒の種類・位置。自玉と自飛車、敵馬などの位置関係を表現する経路がある。近接を常に減点する専用ルールという意味ではない。 |
| 盤全体の利き | `EvaluateControls` | 両玉の位置を条件に、各マスの駒・攻守の利きを評価。安全性の情報が玉周囲8マスだけに限定されるわけではない。 |
| 飛び駒 | `EvaluateSlidingPieces` | 飛・龍、角・馬、香の利きの到達点と玉、利き先の駒の関係。馬の侵入を全く見ていない実装ではない。 |
| 支持形の実験項 | `HasPawnSupportChain` / `EvaluateSupportChain` | 2〜8筋の5段目の歩、1段後ろで歩に利く金銀、それを支える別の金銀。各側に有無を1回だけ判定。玉位置・敵馬・敵桂・敵の利き・対応の急所・ピンは直接参照しない。 |

実際にそれぞれ何点と評価するかは学習済みパラメータと局面による。
表現できることと、十分な重みで正しく評価できることは異なる。
今回、既存の安全性項目を個別に取り出した寄与点数までは測定していない。

## 合算と探索への経路

`EvalDetail::ComputeFinalScore` では、支持形は利き・2駒関係・玉安全性・飛び駒と
加算される。支持形と安全性を条件付きで結ぶ仕組みは実験項にない。
支持形10は先手側の有無から後手側の有無を引き、進行度に応じて
概ね `10 × (1 − progress)` cp相当になる。双方成立なら相殺し、整数化の丸めがある。
進行度や手番用の重みを実験項自体は変更しない。

したがって「玉安全性を消して厚みだけを評価している」のではない。
一方で「危険な形なら支持形の加点そのものを無効にする」という条件もない。
この条件を足せば改善するとは、今回の観察だけからは言えない。
既存項との重複や、正当な反撃を抑える可能性も検討が必要。

`src/search.cc` の通常探索・静止探索は静的評価を参照し、枝刈りやstand patにも使う。
実戦局面で支持形がなくても、未着手の探索枝での加点が選択に影響する余地がある。
逆に、直後の局面で支持形が成立しただけで、その手を加点のために選んだとは言えない。
思考時間制限、置換表、先行手順の違いもあるため、静的差と探索差を区別する。

## 今回の限定照合

組4の第7/8局、組7の第13/14局について、総手数32〜48の全17局面ずつ、
計68局面を既存のネイティブ支持形検査器で0/10照合した。
成果物は `results/teatsui-king-safety-review-2026-11-07/`。
新規探索・再対局・ビルドは行っていない。

| 組・実戦設定 | 32〜48手の支持形 | 同一局面を0/10で静的比較した差 |
| --- | --- | --- |
| 組4・第7局（10） | 両側とも全17局面でなし | 全て0 |
| 組4・第8局（0） | 32〜46手で先手に成立 | 32手で先手+6。48手では不成立で0 |
| 組7・第13局（0） | 両側とも全17局面でなし | 全て0 |
| 組7・第14局（10） | 42手の後手だけ成立 | 後手+6（手番の先手視点では−6）。43手以降消滅 |

第8局で支持形が成立していても、実戦設定は0なので加点はされていない。
第14局の42手は5五歩・6四銀・5三銀の連鎖。43▲同歩で消滅し、
44△同銀で銀が5五に進んでも、この実験項は歩を条件にするので成立しない。
2筋の歩を伸ばした後の36/40/48手の実戦局面にも支持形の加点はない。
それでも探索枝への影響は排除できず、実戦静的評価だけで原因を結論しない。

Solが `static_audit.py` と `static_audit.json` を作成し、親がプロトコルと結果を確認。
検査バイナリは既存 `results/thickness-dialogue/support-chain-native-2026-10-31/check`。
同時期のmanifestと、バイナリ・検査ソース・evaluation.cc/h・params.binのハッシュが一致。
実行前後で対象ファイルと棋譜が不変。全リンク元ソースの再ビルド検証はしていない。
検査器内で全評価・キャッシュ・null move・支持形の式をassert照合。
出力はShinONでの手番側の静的総評価。進行度は内部検証のみで数値出力されないため、
進行度の推定値や既存玉安全性項だけの寄与を報告していない。


## 次の設計判断

支持形は狭い形の指標であり、「手厚い将棋」全体の代用にはしない。
ただし今回の2例から、玉安全性の新項目や支持形の停止条件を直ちに追加しない。

因果をさらに調べる場合は、組7の加点10の保存履歴から35手終了時
（△2四歩の前）と41手終了時（△5五歩の前）の2局面に限定する案がある。
同じ履歴・新規プロセス・同一バイナリで0/10を比較し、時間揺れを減らすため
固定ノード数を用いる。ノード上限・停止条件を先に固定し、同一条件の再現性検査も
必要最小限に含める。これは未実装・未実行の案で、今回の検証に紛れ込ませない。
候補手の変更が再現しても棋力改善や敗着の証明ではなく、再現しなければ
この例を加点の失敗教師にせず、原因未確定として区切る。
