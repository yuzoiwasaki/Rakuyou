# 対話参照例の局面注釈：点数を付けずに支持形と利きを見る

[設計基準](2026-11-07-style-design-criteria.md)の6例・15局面に限定し、
支持形と相手の利きを確認する注釈を作成した。エンジンの評価・探索・運用設定は変更しない。

## 注釈の範囲

- 支持形：既存実装と同じ5段目の歩・その1段後ろの金銀・支える別の金銀。
  有無に加え、該当する駒の座標を示す。
- 玉とその周囲：玉のマスと盤内の隣接マスごとに相手の利き元と味方の守備駒を表示。
  味方玉の利きは守備駒一覧から除外。数は上限なしであり、C++安全性項の最大3とは異なる。
- 金銀：未成の金銀それぞれに利く敵味方の駒を表示。
- 自陣3段内の相手駒：先手なら7〜9段、後手なら1〜3段にいる相手駒。
  座標による一覧であって、危険な侵入・有効な攻めの認定ではない。

利きは駒の動きと遮蔽物に基づく幾何的なもの。飛び駒は最初の占有マスを含めて止まり、
味方駒のあるマスへの利きも支持として含める。ピンや自玉への王手放置を考慮しない。
利きがあることは、合法に取れること・得になる攻め・安全な逃げ場の意味ではない。
持ち駒からの仮想的な打ち込みや相手の次手の探索は行わない。
金銀の前進や相手の利きの数から、厚み・危険度・好みの総合点を算出しない。

## 入出力と保全

入力：`results/teatsui-review-reference-2026-11-07/cases.json`。
出力：`results/teatsui-position-annotations-2026-11-07/`。
局面は元の棋譜ハッシュ、全履歴、保存SFENと照合し、ユーザーの判断は計算注釈と分ける。
旧棋譜・既存UI・凍結した実験ファイルは上書きしない。

支持形のC++照合は既存 `support-chain-native-2026-10-31/check` で行い、
バイナリ・検査ソース・evaluation.cc/h・params.binを以前のmanifestと照合した。
`native_reference.py` / `native_reference.json` が根拠。ビルド・探索は0回。
15局面のうち支持形があるのは第8局32手目の先手のみ。他の14局面は両側ともなし。
この数は選んだ既知の参照例での頻度であり、一般の出現率を示すものではない。

## 検証と次の確認

実装：`annotate.py`、`annotations.json`、`index.html`。
6つの事例と各局面、注釈対象の先後を選び、盤面の表示を切り替えられる。
支持関係、玉周辺の相手の利き、相手が利く金銀、自陣3段内の相手駒を個別に表示する。
表には利き元の駒と座標を全て示す。ユーザーの選好・局面判断は元の記録を保持する。

意味のある6検査を実施：飛び駒の遮蔽と占有マス、双方の駒の動き・成駒、
ピンでも幾何的な利きは残ること、玉周辺と金銀での玉の支持の扱い、支持形の条件、
元棋譜再生とユーザー判断の保全、実15局面の先後反転・左右反転の整合性を含む。
金銀への支持一覧では味方玉の利きも表示し、玉周辺の一覧でのみ玉自身を除外する。
支持形の有無は15局面・両側30判定すべてでC++参照と一致。
Nodeによる画面操作の480通り（15局面×2側×16表示設定）と事例ごとの担当色初期選択も検査した。
ブラウザでの目視確認は未実施。
攻撃マップ全体のC++実装との一致は検証しておらず、ネイティブ安全性項の再現値ではない。

組6の48手目は7四金に8三銀の支持があり、幾何的な敵の利きはなし。
49▲7五歩打で7五歩からの利きが加わるが、8三銀の支持も残る。
50△7三金後は7二金・8一桂の支持がある。
支えられた金でも相手の歩で押し戻される例として確認できる。
単なる支持駒数を、持続する抑制力と同一視しない。

この注釈は新しい評価関数ではなく、候補特徴を検討するための観察用。
支持形がない好ましい形を拾う必要と、前進が相手を抑えるとは限らない問題を分ける。
最初の画面確認は組6の48→49→50手。49▲7五歩で7四金への利きが増え、
50△7三金で配置が変わることを具体的に確認する。
ただし、これだけで「歩で追える金は減点」という規則にはしない。
